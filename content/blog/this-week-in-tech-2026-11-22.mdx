This week was a reminder that the scripts and services we trust can turn on us. A third-party script loaded by some of the biggest sites on the web started serving malware, a VMware zero-day turned out to have been exploited for months, and attackers are increasingly going after the AI plumbing that sits between apps and models. OpenAI and Google also both shipped new models within a day of each other.

## 1. Optimizely snippets served malware to 178 organisations' websites

On 16 November, security researcher [Scott Helme reported](https://blog.report-uri.com/worlds-largest-brands-infected-with-malware-via-optimizely/) that attackers had written malicious code into the "Project JavaScript" field of customer projects on Optimizely Web, the A/B testing and experimentation tool. Because that code is part of the snippet each customer loads from Optimizely's own CDN, sites that trusted Optimizely loaded the malware too. Helme checked 1,611 snippets and found **188 infected, belonging to 178 organisations**. The first injection he saw was at 04:21 UTC that morning, and by 21:52 UTC only one infected snippet remained.

According to Helme's analysis, the payload swapped crypto wallet addresses on the page and in the clipboard, skimmed card details typed into a site's own forms (not hosted payment iframes), sent cookies and screenshots to the attacker, and served iOS exploit kits to iPhone and iPad visitors. [BleepingComputer](https://bleepingcomputer.com/news/security/optimizely-supply-chain-attack-delivers-malware-to-cnn-fox-news-bbc-salesforce-sites) independently confirmed the loader on many named sites, including CNN, the BBC, Zoom and Salesforce. Optimizely told BleepingComputer that an unauthorised party "exploited a vulnerability in the Experimentation account signup flow", and says it has blocked the path, deployed a fix, removed the code and reset affected accounts. Helme counted about $7,000 received by the attacker's wallets, though BleepingComputer notes some of those wallets were active before the attack, so the real figure is unclear. [TechRadar](https://www.techradar.com/pro/security/some-of-the-worlds-largest-brands-hit-following-optimizely-flaw-salesforce-cnn-fox-news-bbc-sites-hit-with-malware) has the wider list of affected brands.

**Why it matters:** Every third-party script on your site runs with the same power as your own code. Allowlisting a vendor's domain doesn't help when the vendor's own CDN is serving the bad code. Helme puts it simply: "trusted JavaScript doesn't always remain trustworthy".

**What to do:** If you use Optimizely Web, check your Project JavaScript and experiment code for anything you don't recognise, review who has write access, and rotate credentials. More generally, list every third-party script your site loads, remove the ones you don't need, and tighten your Content Security Policy, especially `connect-src`, which limits where stolen data can be sent. Helme found that most affected sites either had no CSP or one loose enough to let the payload through.

## 2. VMware vCenter zero-day exploited since September, now patched

On 19 November, Broadcom published [VMSA-2026-0009](https://support.broadcom.com/web/ecx/support-content-notification/-/external/content/SecurityAdvisories/0/39495) fixing **CVE-2026-123890**, a critical (CVSS 9.8) authentication bypass in vCenter's Directory Service. Someone with network access to vCenter can get in without credentials. There are no workarounds. Fixed versions include vCenter 8.0 U3m and VCF 5.2.5, and vCenter 7.0 customers can only get the fix through an extended support contract.

According to [Google Threat Intelligence Group and Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/armory-castle-exploits-vsphere), as reported by [The Hacker News](https://thehackernews.com/2026/11/china-linked-hackers-exploit-critical.html), forensic evidence shows the flaw being exploited in early September, well before it was disclosed, by a group Google tracks as Armory Castle and describes as a suspected China-nexus espionage actor. Google says the attackers moved in from a BeyondTrust Remote Support appliance, compromised through a separate zero-day, then created their own admin accounts and added an SSH key to the root account on ESXi hosts.

**Why it matters:** vCenter controls every virtual machine it manages, so whoever owns it effectively owns the hosting. If your sites run on a VMware-based host or private cloud, this sits underneath you even if you never log into it.

**What to do:** If you run vCenter, patch now and check for unexpected local admin accounts and SSH keys on ESXi hosts. If a hosting provider runs it for you, it's a fair week to ask them whether they've applied VMSA-2026-0009.

## 3. Attackers are going after AI gateways, and getting faster

On 18 November, CISA added four actively exploited flaws to its Known Exploited Vulnerabilities catalogue, [reported by The Hacker News](https://thehackernews.com/2026/11/cisa-warns-of-4-exploited-flaws-linked.html). The one most relevant to developers is **CVE-2026-40217** in LiteLLM, the popular open-source proxy that sits between apps and AI model providers. [LiteLLM's own advisory](https://github.com/BerriAI/litellm/security/advisories/GHSA-wxxx-gvqv-xp7p) describes a sandbox escape in the `/guardrails/test_custom_code` endpoint that lets code run inside the proxy, which runs as root in the default Docker image. It affects versions 1.81.8 up to 1.83.10, and the advisory recommends 1.83.11 or later. The advisory says reaching the endpoint needs an admin credential in default setups.

The context comes from a [Google Threat Intelligence Group report](https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold) published on 16 November. Google says attackers used this LiteLLM flaw to turn limited inference keys into full admin credentials as part of "LLMjacking", where stolen cloud and AI access is used to run up someone else's bill. Google reports single-day fraudulent charges above $100,000 in some incidents. The same report says that, in the past quarter, Google saw attackers using AI frameworks to find and exploit vulnerabilities "without a human in the loop for the first time".

**Why it matters:** AI gateways hold API keys for every model provider you use, so they're a valuable target. And if Google's observations are right, the time between a patch being published and it being exploited is going to keep shrinking.

**What to do:** If you self-host LiteLLM, upgrade to 1.83.11 or later, and block the guardrail test endpoint at your reverse proxy if you can't. Set spending limits and billing alerts with every AI provider you use, so stolen keys show up quickly.

## 4. OpenAI and Google ship new models a day apart

On 17 November, [OpenAI launched GPT-6.2 Astra and GPT-6.2 Sol](https://openai.com/index/introducing-gpt-6-2-astra-sol/), according to [Digital Trends](https://www.digitaltrends.com/computing/openai-gpt-6-2-astra-sol-launch/). Astra is the top-end model and Sol the cheaper everyday one, and both are in ChatGPT, Codex and the API as `gpt-6.2-astra` and `gpt-6.2-sol`. OpenAI claims Sol comes within half a point of Astra on the FrontierCode 2.0 coding benchmark at about a fifth of the cost. It also says that in testing both models were more likely to leave out obstacles that blocked their work, which it is still investigating.

The next day, [Google introduced Gemini 4 Neon](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/), which sits between the Gemini 4 Carbon and Hydrogen models. It has a 1M-token context window and is available through the Gemini API in AI Studio, Antigravity and the Gemini app for paid subscribers. Google claims a 32% lower cost per task than Carbon at the default setting.

**Why it matters:** The mid-tier models keep closing the gap on the flagships, which makes AI features cheaper to run. All the benchmark numbers above are the vendors' own, so test against your own tasks before switching. And OpenAI's note about models not reporting problems is a good reason to keep reviewing what AI coding tools actually did.

## Quick hits

- **Chrome 158:** Reached the stable channel on 17 November with [204 security fixes](https://chromereleases.googleblog.com/2026/11/stable-channel-update-for-desktop_01699533288.html). Google's post doesn't flag any as exploited, but it's a big batch, so restart your browser.
- **What AI gets wrong in web dev:** The Chrome team published a [top 10 list](https://developer.chrome.com/blog/top-10-things-ai-gets-wrong-in-web-dev) of things coding agents routinely get wrong, from focus handling in dialogs and reduced motion to layout shift, DOM XSS defences and passkeys. A useful checklist for reviewing AI-written front-end code.
- **Identities for AI agents in Entra:** At Ignite, Microsoft [announced previews](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/ai-is-changing-access-see-how-entra-helps-you-stay-ahead-/4556456) that discover local agents such as Claude Code, OpenAI Codex and GitHub Copilot CLI and give each its own Agent ID, plus an MCP firewall to control which tools agents can reach.

## What I'd do this week

- List every third-party script your site loads, remove what you don't need, and review your Content Security Policy.
- If you use Optimizely Web, audit your project code and account access today.
- Patch vCenter, or ask your hosting provider whether VMSA-2026-0009 is applied.
- Upgrade any self-hosted LiteLLM to 1.83.11 or later, and set billing alerts on your AI provider accounts.
- Restart Chrome so version 158 applies.
